## 一、项目一句话定义

宠馨智是连接宠物主人和宠物医院的院后慢病护理协同平台：医生负责诊疗决策和签署护理方案，AI管家负责解释医嘱、拆分每日任务、监督执行、整理趋势、发现漏执行和风险，并把异常回传给医生。

核心闭环：

```text
宠主建档并授权医院
→ 医院分配主治医生
→ 医生诊断并签署护理方案
→ AI管家把医嘱拆成每日任务
→ 宠主和家人执行、打卡、上传报告
→ 数据进入长期健康档案
→ 规则与AI发现变化、漏执行和风险
→ 异常进入本院医生待处理队列
→ 医生审核并修改方案
→ 次日任务自动同步
→ 复诊指标验证护理方案效果
```

医疗边界：AI不独立诊断、不改变疾病分期、不新增或调整药物；异常必须建议联系兽医或及时就医。

## 二、唯一正确的软件架构

```text
一个微信小程序
├── pet_owner：宠主手机页面
└── doctor：医生手机页面

一个独立Web管理后台
└── admin：开发者/平台管理员电脑页面

一个Node.js API
├── 登录与角色
├── 宠物/病例/护理/打卡
├── 医院授权与数据隔离
├── AI与知识库
└── 管理接口

一套共享数据库和私有文件存储
└── PostgreSQL + RLS + Storage
```

不做三个小程序，不做三套后端，不允许管理员功能进入普通小程序。

- [ ] 每项任务包含时间、频率和执行说明。
- [ ] 明确AI允许提醒的范围。
- [ ] 明确哪些情况必须联系医生或急诊。
- [ ] 医生签署后才对宠主生效。
- [ ] 每次修改产生新版本、修改原因和修改人。
- [ ] 医生修改后，宠主次日任务自动更新。
- [ ] 没有当天打卡时，医生基础方案仍然显示和执行。

### 4. 宠主院后护理

- [ ] 首页只突出“今天要做什么、有没有风险、下一步是什么”。
- [ ] 基础模式无需设备：食欲、精神、饮水变化、排尿变化、呕吐、任务完成。
- [ ] 普通设备模式：体重、饮水毫升、尿团数量。
- [ ] 专业设备模式：血糖、血压、尿检和硬件数据。
- [ ] 多位家庭成员共同护理，记录谁完成，避免重复喂药。
- [ ] 药物、饮食、补液、监测和复查任务统一管理。
- [ ] 漏执行提醒；不能把“没记录”当成“正常”。
- [ ] 每次保存显示档案编号、与上次变化、触发原因、是否通知医生和预计处理时间。
- [ ] 记录进入7/14/30天趋势和长期档案。

### 5. 医生异常队列

- [ ] 红色：疑似紧急，需要立即关注。
- [ ] 黄色：等待处理，包括连续恶化、漏执行或漏复查。
- [ ] 绿色：稳定，无需主动处理。
- [ ] 医生可以确认、联系宠主、写处理意见和解决异常。
- [ ] 每个异常有接收人、处理时限和超时升级。
- [ ] 医生看到原始记录，不只看到AI摘要。
- [ ] AI只汇总，不替医生作诊疗决定。

- [ ] 找不到依据时明确说“知识库依据不足”。
- [ ] 药物调整问题必须转给开方兽医。
- [ ] 紧急症状优先就医，不能被普通回答覆盖。

## 五、第一轮医院试点必须完成（P1）

- [ ] 只选择1家愿意共同打磨的医院。
- [ ] 1名内科或肾病方向兽医作为临床负责人。
- [ ] 10–20只已经确诊的CKD猫作为首批病例。
- [ ] 运行30–60天，不直接大规模投放。
- [ ] 衡量任务完成率、复诊到诊率、异常响应时间、医生沟通时间和失访率。
- [ ] 收集宠主易用性反馈和医生工作负担反馈。
- [ ] 复诊结果验证护理方案是否有效，不宣传没有证据的治愈率或死亡率下降。
- [ ] 完成一次病例授权转交和一次撤回授权测试。

- [ ] CKD知识库：猫100条、犬100条，经兽医逐条审核。

- [ ] 使用向量检索和重排序替代当前简单关键词检索。

- [ ] 商城只展示真实自营或正式合作商品，不生成虚构品牌和库存。
- [ ] 商品推荐与医疗建议分离，医生和AI不能为了销售改变护理判断。

- [ ] 智能饮水盆、喂养盆、体重秤、猫砂盆先定义数据协议，再做硬件样机。
- [ ] 硬件异常不能直接诊断，只能生成监测记录和风险提示。
- [ ] 主题皮肤、宠物可爱化视觉和品牌内容持续优化，但不影响专业信息阅读。

## 九、怎么运行

### 1. 浏览器预览版

```bash
pnpm dev
```

浏览器打开 `http://127.0.0.1:3000`。这主要用于看界面，不代表真实云数据已接通。

### 2. Node.js API

```bash
cp .env.api.example .env.api
```

由负责人在本机填写真实密钥，然后：

```bash
set -a
source .env.api
set +a
pnpm backend:preflight
pnpm api:check
pnpm api:test
pnpm api
```

检查：

```text
http://127.0.0.1:8787/api/v1/health
http://127.0.0.1:8787/api/v1/ready
```

### 3. Web管理后台

复制 [admin-web/.env.local.example](../admin-web/.env.local.example) 为 `admin-web/.env.local`，填写API地址，然后：

```bash
pnpm admin:dev
```

### 4. 微信小程序

1. 安装微信开发者工具。
2. 导入 [miniprogram目录](../miniprogram/README.md)。
3. 把 `project.config.json` 的AppID换成正式AppID。
4. 在 [config.js](../miniprogram/config.js) 写正式HTTPS API地址。
5. 真机测试微信登录、角色跳转和文件上传。

## 十、云端模型切换为本地/私有模型

### 必须先理解

“本地AI”只表示模型推理不调用第三方云模型，并不表示小程序可以脱离服务器。正式小程序仍需要API、数据库、文件存储、账号和权限服务。

有两种方式：

1. 电脑本地演示：Node API和Ollama都运行在你的电脑上，只适合开发测试。
2. 私有化生产：Ollama/vLLM和模型运行在你控制的云服务器或医院私有服务器上，小程序通过HTTPS API访问。

### 电脑本地演示步骤

1. 安装Ollama。
2. 下载示例模型：

```bash
ollama pull qwen3:8b
```

3. 保持Ollama运行。
4. 加载 `.env.api` 后，再加载 [.env.local-ai.example](../.env.local-ai.example)：

```bash
set -a
source .env.api
source .env.local-ai.example
set +a
pnpm ai:smoke
pnpm api
```

5. `pnpm ai:smoke` 返回“宠馨智AI连接成功”后，再测试知识库问答和医嘱拆解。

### Docker私有部署步骤

```bash
docker compose -f compose.yaml -f compose.local-ai.yaml up -d --build
docker compose -f compose.yaml -f compose.local-ai.yaml exec ollama ollama pull qwen3:8b
```

CPU服务器运行8B模型可能很慢。比赛演示可先在内存充足的电脑上测试；真实多人使用需要GPU、并发限制、模型监控、提示词与知识库评测。模型换成本地后，AI安全边界、知识库审核和医生签署流程仍然不能取消。

### 云端与本地切换只改这些变量

云端：

```text
AI_PROVIDER_MODE=cloud
AI_API_URL=云模型完整chat/completions地址
AI_API_KEY=真实密钥
AI_MODEL=模型名称
```

本地：

```text
AI_PROVIDER_MODE=local
AI_API_URL=http://127.0.0.1:11434/v1/chat/completions
AI_API_KEY=
AI_MODEL=qwen3:8b
```

小程序、医生端和管理后台不需要因为换模型而重写。

## 十一、怎么安全转移到另一台电脑

### 推荐方式：私有Git仓库

1. 在GitHub或Gitee新建私有仓库。
2. 只上传源代码、迁移、文档和非敏感配置模板。
3. 不上传 `.env.api`、管理员密码、微信AppSecret、Service Role Key、AI Key、`node_modules`、`.next`。
4. 新电脑安装Git、Node.js、pnpm、微信开发者工具和Docker。
5. 克隆私有仓库并执行 `pnpm install`。
6. 在新电脑重新创建本地密钥文件。
7. 真实数据通过数据库备份恢复，不通过微信或U盘随意复制。

### 临时压缩包方式

可压缩整个项目目录，但应先排除：

```text
.env.api
.env.local
admin-web/.env.local
node_modules/
.next/
admin-web/.next/
```

如果压缩包包含真实病例、证件或密钥，必须加密并单独传输密码。Mac和Windows都使用UTF-8文件名；不要修改迁移文件时间戳和顺序。

## 十二、哪些操作必须由负责人本人完成

- 微信、云服务器、域名、备案和模型平台的实名认证、付款与验证码。
- 确定营业执照主体、客服电话和隐私联系人。
- 签订医院、医生、品牌、保险或硬件合作合同。
- 审核隐私政策、用户协议和数据处理协议。
- 把真实密钥安全填写到本机或云平台，不把密钥发到聊天中。
- 最终确认哪些医院和医生可以上线。

完成账号和密钥配置后，开发工作可以继续执行迁移、部署、联调、测试和发布。

## 十三、现阶段不要做错的事

- 不用网络资料虚构合作医院、医生、保险和商品。
- 不把静态展示页当成已经上线的软件。
- 不让AI独立诊断、调药或自动改变分期。
- 不把商城、广告、保险和硬件排在护理闭环之前。
- 不把没有设备的家庭挡在产品之外。
- 不把一次异常读数直接等同于疾病恶化。
- 不上传受版权保护的整篇资料作为商业知识库；保存结构化摘要、短引用和完整出处，全文需授权。
- 不宣传未经临床试点证明的治愈率、死亡率下降或固定效果。

## 十四、下一步唯一优先顺序

1. 负责人创建数据库、小程序、模型、服务器和域名账号。
2. 开发者执行迁移、存储、管理员和API部署。
3. 真机打通宠主—医生护理闭环。
4. 完成消息、异常处理、隐私、监控和备份。
5. 进行1家医院、10–20只CKD猫的封闭试点。
6. 根据真实反馈调整产品，再考虑比赛展示、扩病种和商业模块。

做到第5步，宠馨智才从“完整原型”变成“有真实使用证据的创业项目”。
